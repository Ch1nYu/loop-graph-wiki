給 AI 與人共讀的知識庫：把「一句話 Prompt」升級成「可驗證的工作流」。

這個 Wiki 是什麼

這個 Wiki 的主題是 Loop / Graph Engineering：如何把一個模糊的工作（例如「做一份教學簡報」）拆成 AI 能執行、能檢查、能退回的流程。它結合三個來源脈絡：

  1. Week 10 課程：Harness、Loop、Graph 三層工程，以及 LLM Wiki 與簡報工作流。
  2. Week 9 的 AI 閱讀筆記：Anthropic 的 agent 設計、LangGraph 的圖與狀態、Harness 工程、自我改進迴圈。
  3. 本專案的實際執行：從 7 篇來源生成 13 頁教學簡報的完整紀錄。

主要讀者：大學部高年級或研究所初學者，用過 ChatGPT 但沒有寫過 agent workflow；以及下游的簡報生成 AI。

快速回答

Q：Loop 和 Graph 的差別是什麼？ A：Loop 是「一個節點加一條回到自己的邊」，Graph 是「多個節點加條件邊與退回邊」。Loop 由 AI 在規格內決定下一步，Graph 由人類事先畫好流程（Prompt、Loop、Graph 怎麼選？）。

Q：為什麼不能只寫 Prompt？ A：一次性任務可以；但如果你一直重複說同樣的修正指令，就代表你需要 Loop；如果不同階段有不同驗收標準，就代表你需要 Graph（Prompt、Loop、Graph 怎麼選？）。

Q：為什麼不能讓 AI 自己檢查？ A：生成者會有自我護航的偏見；獨立審查必須用新上下文，只給成品與來源（雙軌驗證：程式檢查與獨立 AI 審查）。

Q：什麼是 State as Files？ A：把每個節點的狀態與產出存成檔案，讓流程可以 diff、重跑、只退回某一關（State as Files：資料夾就是流程的記憶體）。

概念 · graph-nodes-edges

Graph 的基本元素：節點、邊、條件邊、狀態

一句話：節點是「誰做事」，邊是「下一步去哪裡」，條件邊是「依什麼決定」，狀態是「做到哪裡」。

從圖論看三種結構

課程用圖論把 Prompt、Loop、Graph 放在同一個框架裡（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.3）：

  1. Prompt：只有一個節點 A，跑一次就結束。
  2. Loop：一個節點 A，加一條回到自己的邊（A ↺）。
  3. Graph：多個節點（A → B → C），加上條件分支與退回邊。

這個視角的好處是：你不會把 Graph 想成「比較高級的 Loop」，而會看到它們的結構差異——Graph 多了多節點與條件邊，因此可以分工、可以並行、可以精準退回。

四個基本元素

節點（Node）

節點是一個處理單元，可以是一個 LLM 呼叫、一個工具、一個 Python 函式，或一個人工審核關卡。LangGraph 的節點可以是 call_model、action、planner、generate 等（Andrew Ng 與 LangChain 的 LangGraph Agent 課程 §Agentic Workflow 基礎）。

節點的設計原則是單一職責：一個節點只做一件事，輸入與輸出都是明確的檔案或狀態欄位。例如「抽證據卡」只負責從單篇來源抽卡，不負責寫大綱。

邊（Edge）

邊是固定的流向：A → B 表示 A 完成後一定去 B。邊讓流程可預測，也讓「不能跳關」變成結構上的保證（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.3）。

條件邊（Conditional Edge）

條件邊是決策分流：依某個條件決定去哪裡。例如「覆蓋率 < 3 頁 → 停止；否則 → 抽證據卡」（Andrew Ng 與 LangChain 的 LangGraph Agent 課程 §Agentic Workflow 基礎）。

條件邊是 Graph 的靈魂：沒有條件邊，Graph 只是一條 pipeline；有條件邊，才能做分支、重試與退回。

狀態（State）

狀態是流程的記憶體：目前做到哪一關、已經通過哪些檢查、有哪些檔案。LangGraph 用 TypedDict 定義 State，用 Annotated[..., operator.add] 讓訊息累加，未標註的欄位則覆寫（Andrew Ng 與 LangChain 的 LangGraph Agent 課程 §Agentic Workflow 基礎）。

狀態可以是記憶體中的物件，也可以是檔案（State as Files）。本專案採用後者：每個節點的產出都是執行資料夾下的實體檔案，因此可以 diff、可以重跑、可以只退回某一關（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §5.3(4)）。

一個最小 Graph

[檢索] → <覆蓋率 ≥ 3?> ──否──▶ [停止]
              │是
              ▼
         [抽證據卡] → [寫大綱] → [寫逐頁稿] → [渲染] → [交件]
                            ▲            │
                            └──退回──────┘

這個 Graph 有四種邊：

  • 固定邊：檢索 → 抽卡 → 大綱 → 逐頁稿 → 渲染 → 交件。
  • 條件邊：覆蓋率檢查 → 停止或繼續。
  • 退回邊：逐頁稿檢查失敗 → 退回該頁重寫。
  • 終止邊：交件或停止。

Graph 與 Pipeline 的差別

維度PipelineGraph
流向單向有分支、有迴圈、有退回
錯誤處理整條重跑錯在哪一關，退回哪一關
並行較難可以扇出/扇入
適用步驟固定的簡單任務多階段、需要條件判斷與復原的任務

課程用「公文流程」比喻 Graph：系辦 → 院辦 → 教務處，每一關有明確職責，不能跳關，哪一關卡住就退回特定的一關（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.3）。

非確定性節點與 Guards

Graph 的節點不一定是確定的程式；很多節點是 LLM 呼叫，輸出有隨機性。課程提到現代 agent graph 的新點在於：非確定性節點、LLM routing 的邊，以及 guards 防護（前 Google 工程師的 AI Agent 系統設計課 §第四階段）。

因此，Graph 不能假設每個節點都會成功；每個 LLM 節點都應該有：

  • 明確的輸入與輸出格式。
  • 失敗時的重試或退回規則。
  • 輸出驗證（例如 JSON schema、關鍵字、長度）。
  • 必要時的人工審核。

Checkpoint 與時間旅行

LangGraph 的 Checkpointer 在每個節點前後保存狀態快照，配合 thread_id 實現多會話隔離與斷點續傳；get_state_history 可以列出歷史快照，用過去的 thread_ts 重新執行，實現時間旅行（Andrew Ng 與 LangChain 的 LangGraph Agent 課程 §Checkpointer 與 Thread、§時間旅行）。

時間旅行不是「改變過去」，而是「從某個快照開一個新分支」，原分支保留。這對除錯很有用：你可以回到「大綱剛寫完」的狀態，換一個教學順序，看看結果差多少。

常見誤解

誤解為什麼錯正確做法
「Graph 就是流程圖，畫好看就好」沒有狀態與條件邊的圖，只是裝飾。每個節點要有輸入、輸出、檢查與退回路線。
「節點越多越專業」節點太多會增加協調成本與失敗點。用單一職責與最小可運作節點數。
「Graph 一定要用框架」小專案用資料夾與腳本就能實作 Graph。先用檔案與腳本，需要持久化再上框架。
「有 Checkpoint 就不會出錯」Checkpoint 只保存狀態，不保證狀態正確。每個節點仍要有驗證。

教學用法

先讓學生用紙筆畫出「從主題到簡報」的流程，標出每個節點的輸入與輸出；再把「如果第 6 頁講錯，要退回哪裡」畫成一條退回邊。學生通常會發現：如果沒有把逐頁稿獨立成節點，就只能整份重跑。

檢查清單

  • [ ] 每個節點是否只有一個職責？
  • [ ] 每個節點的輸入與輸出是否都是明確的檔案或狀態欄位？
  • [ ] 是否有條件邊與退回邊？
  • [ ] 是否有狀態保存與恢復機制？
  • [ ] 每個 LLM 節點是否有輸出驗證與失敗處理？

概念 · harness-loop-graph

Harness、Loop、Graph：三層工程的分工

一句話：Harness 決定「AI 能用什麼」，Loop 決定「AI 怎麼反覆修正」，Graph 決定「誰在什麼時候把控制權交給誰」。

為什麼需要分層

很多人把「AI 做不好」歸咎於模型不夠強，但實際問題常常出在三個不同的層次：模型沒有拿到正確的上下文與工具（Harness）、沒有明確的完成標準與停止條件（Loop）、或是流程的責任與退回路線沒有設計（Graph）。把這三層混在一起，就會出現「在還沒理解行為前就畫流程圖」、「讓同一個模型自己評分」、「無上限重試」等昂貴失誤（Agentic workflow 讓 GPT-3.5 在 HumanEval 達到 95.1% §Harness、Loop 與 Graph）。

課程把生成式 AI 的工程演進整理成五層：Prompt Engineering、Context Engineering、Harness Engineering、Loop Engineering、Graph Engineering（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §1.3）。本頁聚焦後三層，因為它們是「把工作拆成 AI 能做的流程」的核心。

三層各自的問題

層次它回答的問題主要產出缺少它會怎樣
HarnessAI 能看到什麼、能用什麼工具、有什麼權限、狀態存在哪裡？專案規則、任務 Skill、工具、沙箱、權限、記憶、觀測模型拿到錯的上下文、亂用工具、越權修改檔案
Loop這一輪要做什麼、怎麼知道做完了、什麼時候停？目標、限制、驗證、停止條件、觸發人類變成人工迴圈；AI 無限重試或提早收工
Graph有哪些節點、誰把控制權交給誰、錯了退回哪裡？節點、邊、條件邊、狀態、退回路線每次修正都整份重跑；錯誤在最後才被發現

這三層不是替代關係，而是疊加關係。Harness 是地板，Loop 是引擎，Graph 是路網（Agentic workflow 讓 GPT-3.5 在 HumanEval 達到 95.1% §Harness、Loop 與 Graph）。

Harness：把「工作」而不是「模型」放在中心

Harness 的原文定義是「周邊機制：上下文、工具、權限、持續性、控制、安全與可觀測性」（Agentic workflow 讓 GPT-3.5 在 HumanEval 達到 95.1% §Harness、Loop 與 Graph）。另一個說法是：Harness 是針對「工作」裁剪的控制層，不是針對某個模型；模型是商品，Harness 才是資產（How to Build An Agentic Harness using Kimi K3 §五大核心概念）。

在實作上，Harness 包含：

  • 規則：專案手冊定義目標、邊界、寫作規範與完成定義。
  • 技能：任務 Skill 定義特定任務的標準步驟與檢查。
  • 工具與權限：哪些檔案可讀、可寫、可執行；哪些動作需要人工核准。
  • 狀態：檔案、資料庫、ledger 或 checkpoint，讓下一輪能接續。
  • 觀測：log、diff、測試結果、截圖，讓人類能驗收。

課程用「AI Agent = AI Model（大腦）+ Harness（工作裝備）」來描述這個關係（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §1.3）。同一個模型，換一套 Harness，產出品質可能差很多；這就是為什麼與其一直換模型，不如先把 Harness 建好。

Loop：把「修正」寫成規格

Loop 不是「一直重試」，而是「觀察—行動—驗證」的循環，並且有明確的觸發與以證據為基礎的停止規則（Agentic workflow 讓 GPT-3.5 在 HumanEval 達到 95.1% §Harness、Loop 與 Graph）。一個完整的 Loop 要寫清楚五件事：目標、限制、完成標準與驗證、停止條件、觸發條件（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.2）。

Loop 與 Prompt 的差別，不是「有沒有用文字」，而是「誰決定下一步」：寫 Prompt 是寫這一輪要做什麼，人類讀完輸出再寫下一句；寫 Loop 是寫一份會自己執行的規格，系統依檢查結果決定下一步（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.1）。

Graph：把「控制權」畫出來

Graph 用節點與邊描述工作流拓撲，控制允許的下一步、分支、併發、狀態轉移與復原路徑（Agentic workflow 讓 GPT-3.5 在 HumanEval 達到 95.1% §Harness、Loop 與 Graph）。在 LangGraph 的實作裡，節點是處理單元、邊是固定流向、條件邊是決策分流、State 是全域狀態（Andrew Ng 與 LangChain 的 LangGraph Agent 課程 §Agentic Workflow 基礎）。

Graph 的價值不是「看起來比較專業」，而是精準退回：錯在哪一關，就退回哪一關，不用整份重跑（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §5.3）。這也是 Graph 與單純 pipeline 的差別：pipeline 只有往前，Graph 有條件分支與退回邊。

三層如何協作

以「從 Wiki 生成教學簡報」為例：

  1. Harness：專案規則限定可使用的知識庫、唯讀來源與每頁出處要求；任務 Skill 規定節點與檢查。
  2. Loop：逐頁稿節點內部跑「寫一頁 → 對來源 → 修改」的小迴圈，最多 2 輪；渲染節點跑「產生 HTML → 截圖 → 修版面」的小迴圈，最多 3 輪。
  3. Graph：檢索 → 證據卡 → 大綱 → 逐頁稿 → 渲染 → 交件；每個關卡有條件邊與退回路線。

這樣的組合，就是課程說的「Graph 決定大流程，Loop 負責每一格內部的反覆修正」（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §5.3(3)）。

常見誤解

誤解為什麼錯正確做法
「Harness 就是系統提示詞」系統提示詞只是 Harness 的一部分；Harness 還包含工具、權限、狀態與觀測。把 Harness 當成整個工作環境來設計。
「Loop 就是一直重試」沒有停止條件與證據的重試，是無限迴圈。先寫完成標準與剎車，再寫重試。
「Graph 一定比 Loop 好」Graph 的成本與維護複雜度更高；簡單任務用 Graph 是過度設計。先用 Prompt，重複出現再升級 Loop，多階段才拆 Graph。
「三層可以分開看」三層會互相影響：Harness 的權限決定 Loop 能做什麼，Loop 的檢查決定 Graph 的退回邊。設計時一起考慮，但實作時分層負責。

教學用法

教初學者時，先用「Prompt 是一句話、Loop 是一份規格、Graph 是一張流程圖」建立直覺，再用「誰決定下一步」與「錯了退回哪裡」兩個問題區分 Loop 與 Graph。最後用一個真實的小專案（例如這份簡報）示範三層如何疊起來。

檢查清單

  • [ ] 這個任務的 Harness 有什麼？規則、工具、權限、狀態、觀測是否齊全？
  • [ ] 這個 Loop 的目標、限制、驗證、停止條件、觸發是否寫清楚？
  • [ ] 這個 Graph 的節點、邊、條件邊、退回路線是否畫出來？
  • [ ] 三層是否有互相矛盾的地方？（例如 Harness 禁止改檔，但 Loop 要求自動修檔。）

概念 · human-in-the-loop

Human-in-the-loop：人類該在哪一關介入

一句話：人類不該當迴圈，而該當關卡；介入越早、越少，槓桿越高。

從「人工盯場」到「人工關卡」

課程一開始描述的痛點是：人類交辦任務、AI 產出、人類檢查、人類再下指令、AI 再改……在這個模式裡，人類自己變成了那個不斷重複檢查與催促的迴圈（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §1.2）。

Human-in-the-loop 的目標不是「人類什麼都不管」，而是把人類的注意力放在槓桿最高的決策點：需求摘要、大綱、最終驗收。其他時候，讓人類只看報告。

三個高槓桿介入點

介入點人類看什麼為什麼在這裡介入不介入的後果
需求摘要主題、受眾、頁數、語言、來源範圍一旦方向錯了，後面全錯做了 13 頁才發現受眾不對
大綱教學順序、每頁主張、覆蓋率改大綱比改 HTML 便宜簡報做完才發現少一個重要子題
最終驗收成品、檢查報告、獨立審查人類是最後一道判斷自動化流程把錯的東西送上線

課程的 Graph 版流程就把「人類確認大綱」設成一個明確的關卡：不滿意就退回修大綱或補檢索，確認後才寫逐頁稿（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §5.3(1)）。

用 Interrupt 實作關卡

LangGraph 用 interrupt_before / interrupt_after 讓圖在特定節點暫停；前端可以取得當前狀態、修改參數，再恢復執行（Andrew Ng 與 LangChain 的 LangGraph Agent 課程 §Human-in-the-loop）。

這對應到兩個實務需求：

  • 高風險動作前暫停：例如送出郵件、push、部署之前，先讓人類核准。
  • 關鍵決策前暫停：例如大綱確認、來源取捨、預算調整。

Gate 要坐在副作用處

Harness 的文章提醒：UI 強制的 gate 只是建議，真正的 Gate 要坐在副作用處（How to Build An Agentic Harness using Kimi K3 §七大原語）。意思是，如果一個動作會產生不可逆的結果，不能只靠「畫面跳出警告」，而要在執行動作的程式碼裡攔截。

對本專案的啟示：

  • 大綱確認不是「在文件裡寫一句『已確認』」，而是大綱檔裡有明確的確認紀錄與時間。
  • 交件不是「AI 說可以交」，而是所有程式檢查全過、獨立審查通過。

人類介入的成本

人類的時間是最貴的資源。因此：

  • 不要讓人類檢查機器可以檢查的東西（頁數、連結、overflow）。
  • 不要讓人類讀完整份草稿；讓人類讀「差異」與「檢查報告」。
  • 不要讓人類在每個節點都按一次「繼續」；只在真正需要判斷的地方設關卡。

課程用「老闆只需要在最後看一眼報告與成品」來描述理想的 Loop 版流程（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §5.2）。Graph 版則更進一步，把人類放在大綱與最終驗收兩個點。

反模式

反模式問題替代做法
人類全程盯場人類變成迴圈，無法規模化只設關鍵關卡
每個節點都要按確認自動化失去意義只在高風險/高槓桿處暫停
人類直接改 AI 的檔案繞過流程，無法追蹤人類給回饋，AI 按規格修改
沒有確認紀錄不知道人類到底同意了什麼在狀態檔留下確認時間與版本

教學用法

問學生：「如果你只能選三個地方看 AI 的簡報，你會選哪三個？」通常會得到「主題、大綱、成品」。再問：「為什麼不是每一頁都看？」學生會發現：每一頁都看就等於回到人工迴圈。

  • [ ] 人類是否只在需求、大綱、最終驗收等關鍵點介入？
  • [ ] 每個介入點是否有明確的輸入與決策？
  • [ ] 高風險動作前是否有 Gate？
  • [ ] 確認紀錄是否寫進狀態檔？
  • [ ] 人類是否只讀差異與報告，而不是讀完整份草稿？

概念 · loop-five-elements

Loop 的五個要素：目標、限制、驗證、剎車、觸發

一句話：Loop 不是「一直試」，而是「一份會自己判斷下一步的規格」。

為什麼需要五個要素

沒有目標，AI 不知道要做什麼；沒有完成標準，AI 不知道什麼時候算做完；沒有停止條件，AI 會無限重試；沒有觸發，這個 Loop 永遠不會開始。課程把這些整理成五個必寫項目，前三項是「當老闆」的三件事，後兩項是讓迴圈安全自動化的關鍵（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.2）。

這五個要素也對應到零信任的五條規則：僅基於證據前進、限制重試次數、終止狀態必須是驗證輸出或記錄拒絕、權限按步驟分配、開發者自己掌控圖結構（Agentic workflow 讓 GPT-3.5 在 HumanEval 達到 95.1% §零信任五規則）。

五個要素

1. 目標（Goal）

要產出什麼？格式、檔名、存放位置、給誰看？

目標要具體到可以驗收，例如「產出 13 頁的 index.html，每頁至少一個 wiki 引用與一個原始來源，放在專案根目錄」。不要寫「做一份簡報」這種無法驗收的目標。

目標不清楚時，AI 會用最省力的方式交差；例如只讀 3 篇來源就開始寫，或把別人的內容混進來（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §5.1）。

2. 限制（Constraints）

哪些可以做、哪些不能做？

限制包含：可讀寫的檔案、不可修改的原始資料、不可使用的來源、不可超出的頁數、不可改變的語氣與語言。限制的作用是縮小搜尋空間，讓 AI 不會「自作主張」。

例如本專案的規則規定：原始資料唯讀、只能使用 Wiki 的內容、不得把個人隱私或 API Key 放進公開檔案。

3. 完成標準與驗證（Completion Criteria & Verification）

怎麼知道做完了？誰來檢查？

完成標準要包含兩軌：

  • 程式檢查：頁數、出處、數字、連結、overflow 等客觀條件，用腳本判斷。
  • 獨立 AI 審查：忠實度、覆蓋率、教學結構等語意品質，用新上下文判斷。

課程的核心鐵則是：絕對不要叫生出作品的同一個 AI 審自己的作品；審查必須開啟全新對話，只給成品與原始來源（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.2）。

Anthropic 的 evaluator-optimizer 模式也是同一個思路：一個 LLM 生成，另一個 LLM 依標準評估並回饋（Building Effective AI Agents（Anthropic） §Workflow: Evaluator-optimizer）。

4. 停止條件／剎車（Stop Conditions）

做不到或卡住時，什麼時候停？

常見的剎車有三種：

  • 硬上限：最多改 3 輪；改滿就停，附報告請人類處理。
  • 資料不足就停：相關來源少於 3 篇就停止，不用預訓練知識硬湊。
  • 成本上限：token、API 費用、時間或 prompt 增長幅度的上限。

自我改進迴圈的例子用 watcher.md 與 rewriter.md 限制程式碼 ≤ 12 行、prompt 增長 ≤ 20%，這就是用預算當剎車（用 DeepSeek V4 Flash 在 Codex 建立自我改進編碼循環 §自我改進編碼循環）。

5. 觸發條件（Trigger）

什麼時候開始跑？

觸發可以是手動指令（/topic-slides）、檔案更新、排程或事件。沒有觸發條件，Loop 只是一個躺在資料夾裡的規格。

在 LangGraph 裡，節點之間的邊與條件邊就是觸發機制；狀態改變或條件成立時，控制權才往下一個節點走（Andrew Ng 與 LangChain 的 LangGraph Agent 課程 §Agentic Workflow 基礎）。

一份可用的 Loop 規格

目標：產出 13 頁教學簡報 index.html，每頁有 wiki 與原始來源引用。
限制：只能使用 Wiki 知識庫；原始資料唯讀；8–15 頁；繁體中文；不得新增事實。
驗證：
  1. python scripts/check_deck.py → 0 error
  2. python scripts/render_check.py → 0 overflow
  3. 獨立 AI 審查 → 忠實度與覆蓋率 pass
停止：
  1. 全過 → 交件
  2. 改滿 3 輪 → 停止，附報告
  3. 相關 wiki 頁 < 3 → 停止，不生成
觸發：/topic-slides "Loop / Graph Engineering"

常見誤解

誤解為什麼錯正確做法
「完成標準就是『看起來不錯』」主觀標準無法自動判斷，也無法累積。把標準拆成可執行的檢查與獨立的語意審查。
「停止條件會讓 AI 偷懶」沒有停止條件才會讓 AI 無限燒錢。用硬上限與資料不足條件，讓失敗可被看見。
「Loop 越大越好」大 Loop 每次都要整份重跑，成本高、錯誤定位難。把大 Loop 拆成多個小 Loop，錯在哪裡就修哪裡。
「AI 自己說做完就是做完」生成者的自我評估有偏見。用程式檢查 + 獨立 AI 審查。

教學用法

用「請 AI 做一份簡報」當反例，讓學生列出：目標是什麼？限制是什麼？怎麼驗收？什麼時候停？誰來觸發？通常學生會發現自己只寫了目標，其他四項都沒寫。接著把五要素補齊，再比較「有 Loop」與「沒 Loop」的差異。

如果學生寫不出這張表，通常不是 AI 不夠強，而是還沒決定「完成」長什麼樣子。

檢查清單

  • [ ] 目標是否具體到可以驗收？
  • [ ] 限制是否包含可動與不可動的檔案？
  • [ ] 驗證是否同時有程式檢查與獨立 AI 審查？
  • [ ] 停止條件是否包含硬上限、資料不足、成本？
  • [ ] 觸發條件是否明確？
  • [ ] 是否避免讓生成者審自己？

概念 · state-as-files

State as Files：資料夾就是流程的記憶體

一句話：如果一個節點的產出沒有變成檔案，它就等於沒有發生。

為什麼要把狀態存成檔案

檔案不只是備份，而是下一輪的輸入；沒有它，AI 只能從對話裡猜。

課程在 Graph 版工作流裡提出「State as Files」：每一個節點的狀態與產出都是一個實體檔案，因此可以打開來看、可以放進 git、可以單獨重跑（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §5.3(4)）。

這解決了三個問題：

  1. 可追溯：出錯時可以看到是哪一關的哪個檔案有問題。
  2. 可重跑：不用整份流程重來，只要重跑壞掉的那一關。
  3. 可協作：人類可以直接打開檔案，不需要理解整個系統。

本專案的狀態檔

run/
├── sources.md             # N1：檢索結果與覆蓋率
├── cards/                 # N2：每篇來源一張證據卡
├── outline.md             # N3：大綱（含人類確認紀錄）
├── drafts/                # N4：逐頁稿
├── report.md              # N6：檢查與修正紀錄
└── review.md              # N6：獨立審查報告

最終產出是一份 HTML；中間狀態全部留在執行資料夾，不覆蓋、不刪除。這樣即使簡報改了 3 輪，我們還是可以回頭看第 1 輪的檢索結果與大綱，知道當時為什麼做那個決定。

狀態不是只有「檔案」，還有「事件」

Harness 的文章提出 Ledger：有序、僅追加的事件紀錄，先持久化再廣播；讓每一次執行可重播、可審計（How to Build An Agentic Harness using Kimi K3 §BUILD 02）。

檔案是「快照」，Ledger 是「事件流」。兩者互補：

  • 快照告訴你「現在長什麼樣」。
  • 事件流告訴你「怎麼變成這樣」。

對本專案而言，檢查報告就是簡化版的事件流：記錄每一輪發現什麼、改了什麼、為什麼改；機器可讀的檢查結果則是當下的快照。

Checkpoint：可恢復的狀態

LangGraph 的 Checkpointer 在每個節點前後保存狀態快照，配合 thread_id 實現跨請求記憶、中斷續跑與多會話隔離；生產環境可外接 PostgreSQL/Redis（Andrew Ng 與 LangChain 的 LangGraph Agent 課程 §Checkpointer 與 Thread）。

Checkpoint 的價值是「恢復」：如果流程跑到一半中斷，可以從最後一個 checkpoint 繼續，不用從頭來。對長時間的簡報生成流程，這可以節省大量重複工作。

時間旅行：從舊快照開新分支

get_state_history 可以列出歷史快照，用過去的 thread_ts 重新執行，實現時間旅行；這會產生新分支，原分支保留（Andrew Ng 與 LangChain 的 LangGraph Agent 課程 §時間旅行）。

對寫作的啟示：如果你不確定「先講 Loop 再講 Graph」還是「先講 Graph 再講 Loop」比較好，可以從「大綱完成」的快照開兩個分支，各寫一版，再比較。這比在腦中想像更可靠。

記憶的四個類型

課程提到 Harness 注入四類記憶：程序記憶（技能/如何行動）、語義/耐久事實（私有知識）、事件記憶（跨對話時間序列）、工作記憶（當下上下文）（前 Google 工程師的 AI Agent 系統設計課 §Agent Harness、記憶體系）。

對應到本專案：

  • 程序記憶：任務 Skill 與 workflow 定義。
  • 語義記憶：Wiki 的 concept 與 source 頁。
  • 事件記憶：檢查報告與 Wiki 變更日誌。
  • 工作記憶：簡報規格與執行中的逐頁稿。

這個分類可以幫助你判斷「這個資訊應該放在哪裡」：技能放規則檔、事實放知識庫、過程放日誌、當前任務放執行資料夾。

概念 · stop-conditions

停止條件：沒有剎車的 Loop 只是燒錢

一句話：Loop 的品質不只看它會不會改，更看它知不知道什麼時候該停。

為什麼停止條件是核心

課程有一句很重的話：「沒人看管的 loop，就是在沒人看管下犯錯（且燒錢）的 loop。」（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.2）一個沒有停止條件的 Loop，會在同一個錯誤上無限重試，消耗 token、API 費用與時間，最後還是沒有解決問題。

實證也支持這個風險：IAL-Scan 掃描 6,549 個 agent 倉庫，找到 68 個確定的無限 agentic 迴圈失敗，精準度 91.9%；其中 95.6% 伴隨 API 成本耗盡或模型拒絕服務（Agentic workflow 讓 GPT-3.5 在 HumanEval 達到 95.1% §實證發現）。

五種常見剎車

1. 硬上限（Hard Cap）

最簡單也最可靠：最多改 3 輪（或 5 輪）。改滿就停，附上報告請人類處理。

課程的建議是：如果改了 3 輪還沒通過，代表問題出在規格或資料，應立即停下來讓人類介入（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.2）。這個數字不是魔法，而是一個「不要再自動燒錢」的界線。

2. 資料不足就停（Stop on Insufficient Data）

如果知識庫裡找不到足夠資料（例如相關頁面少於 3 頁），直接停止並回報，嚴禁 AI 用預訓練知識硬湊（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.2）。

這條規則同時防止幻覺與「偷懶」：AI 不會因為想交差而編造內容，也不會只用最前面的 3 篇來源就假裝讀完了 8 篇。

3. 成本上限（Token / API / Time）

自我改進迴圈的例子用 watcher.md 與 rewriter.md 限制程式碼 ≤ 12 行、prompt 增長 ≤ 20%（用 DeepSeek V4 Flash 在 Codex 建立自我改進編碼循環 §自我改進編碼循環）。這就是用預算當剎車：如果每一輪都讓 prompt 膨脹 20%，幾輪之後就會失控。

對簡報流程，成本上限可以是：

  • 最多 3 輪修改。
  • 最多 15 頁。
  • 最多 7 篇來源。
  • 每次檢查最多 5 分鐘。

4. 進展停滯就停（Progress-Gated Detector）

Harness 的文章提出 Detector：用「明確缺乏進展」判斷卡住，而不是只看「有沒有在動」；並且要先寫誤報測試，避免把「正在編譯」誤判為「掛了」（How to Build An Agentic Harness using Kimi K3 §BUILD 09）。

對簡報流程的啟示：如果連續兩輪檢查都報同一個錯誤，而且修改沒有讓錯誤數量下降，就應該停下來檢查「是不是規格寫錯了」，而不是繼續重試。

5. Fail Closed

如果檢查腳本自己壞掉，不能默默跳過，而要視為失敗（fail closed）。Harness 的沙箱原則是：任一 canary 探針失敗就拒絕啟動，沒有降級模式（How to Build An Agentic Harness using Kimi K3 §BUILD 05）。

對本專案的啟示：check_deck.py 如果 crash，run_all.py 必須回傳非零退出碼，不能印出「檢查完成」就當作通過。

停止條件與零信任

零信任的五條規則裡，有三條直接跟停止有關（Agentic workflow 讓 GPT-3.5 在 HumanEval 達到 95.1% §零信任五規則）：

  • 限制重試次數，否則 swarm 永遠不會停。
  • 終止狀態必須是驗證輸出或記錄拒絕，不能是「AI 說完成了」。
  • 權限按步驟分配，不是整場會話都開放。

這三條可以寫成一個簡單的停止規格：

停止，若：
  1. 所有檢查通過 → 交件
  2. 修改滿 3 輪 → 停止，附報告
  3. 相關來源 < 3 → 停止，不生成
  4. 連續 2 輪同一個錯誤未改善 → 停止，檢查規格
  5. 檢查腳本 crash → 停止，先修腳本

停止不是失敗

很多人把「停止」當成失敗，但其實停止是流程設計的一部分。一個好的停止條件會告訴你：

  • 是資料不足，還是規格不清？
  • 是 AI 不夠努力，還是這個任務不適合自動化？
  • 是檢查太嚴，還是成品真的沒過？

停止後留下的報告，比無限重試更有價值。

反模式

反模式問題替代做法
沒有硬上限無限重試，燒錢設 3 輪上限
資料不足還硬做幻覺、內容空洞少於 3 篇就停
只看「有沒有在動」把卡住誤判為有進展用「錯誤數量是否下降」判斷
檢查腳本壞掉就跳過以為通過，其實沒驗證fail closed
停止後沒有報告不知道為什麼停附上機器可讀的檢查結果與錯誤清單

教學用法

讓學生為自己的 Loop 寫一張「停止卡」：三個停止條件、每個條件的觸發方式、停止後要附什麼報告。學生通常會發現，自己原本只寫了「做到好為止」，這不是停止條件，而是沒有條件。

檢查清單

  • [ ] 是否有硬上限（輪數、頁數、時間）？
  • [ ] 是否有資料不足的停止條件？
  • [ ] 是否有成本上限？
  • [ ] 是否用「進展」而不是「動作」判斷卡住？
  • [ ] 檢查腳本壞掉時是否 fail closed？
  • [ ] 停止後是否附報告？

概念 · information-scoping

資訊與權限隔離：每個節點只能看它該看的

一句話：Graph 的強大不只在於「誰先誰後」，更在於「誰能看什麼、誰能改什麼」。

為什麼要限制視野

如果一個節點能看到所有資料，它就沒有理由只做一件事。

如果每個節點都能看到所有資料、修改所有檔案，就會出現三種問題：

  1. 事實被偷改：渲染節點為了排版，順手改了句子，前面做的忠實度審查就白費了。
  2. 資料張冠李戴：寫 A 論文的段落時，混入了 B 論文的數據。
  3. 責任不清：出錯時不知道是哪一關放進來的錯誤。

課程因此提出「嚴格的資訊與權限隔離」：每個節點只能看它需要的輸入，不能做超出職責的事（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §5.3(2)）。

課程的權限表

流程節點只能看什麼絕對不能做什麼為什麼
證據卡（Cards）單一一篇論文的頁面混入其他論文或外部來源確保每張卡的數據與結論血統純正
逐頁稿（Drafts）確認過的大綱 + 該頁對應的證據卡引用證據卡以外的內容杜絕自由發揮與幻覺
渲染 HTML已通過忠實度審查的逐頁稿修改逐頁稿裡的任何一個字排版節點只負責視覺，不碰事實
檢查關卡該階段成品 + 原始對照來源檢查員自己動手改內容球員不能兼裁判

這張表的重點是：每個節點的「不能做」和「能做」一樣重要。權限不是為了限制 AI 的能力，而是為了讓錯誤可以被定位。

Gate：把關卡放在副作用發生處

Harness 的文章說得更極端：Gate 必須坐在副作用處；UI 強制的 gate 只是建議（How to Build An Agentic Harness using Kimi K3 §七大原語）。意思是，如果一個動作會產生不可逆的副作用（送出郵件、push、部署、刪檔），就必須在動作發生的地方攔截，而不是只在介面上顯示警告。

對簡報流程的啟示：

  • 「渲染」是一個副作用（產生最終 HTML），所以渲染前必須有忠實度關卡。
  • 「交件」是一個副作用（公開部署），所以交件前必須有獨立審查關卡。
  • 「修改原始資料」是一個副作用（污染來源），所以原始資料必須設為唯讀。

ACI：工具介面也是權限設計

Anthropic 的文章提醒：工具設計就是 ACI（agent-computer interface），應投入與 HCI 同等的精力；例如強制絕對路徑可以大幅降低工具呼叫錯誤（Building Effective AI Agents（Anthropic） §Appendix 2）。

權限隔離不只是「設定 ACL」，也包括「工具介面怎麼設計」：

  • 工具參數是否清楚、不容易誤用？
  • 工具是否只暴露必要的操作？
  • 工具是否會回傳足夠的錯誤訊息，讓 AI 知道怎麼修？
  • 工具是否預設安全（fail closed），而不是預設開放？

Worktree 隔離：不要碰使用者的工作區

Harness 文章的另一個原則是：每個 run 使用獨立 worktree，絕不碰使用者 checkout 的分支；reclaim 只收乾淨的 tree，絕不 --force（How to Build An Agentic Harness using Kimi K3 §BUILD 04）。

這個原則可以推廣到任何自動化流程：AI 的修改應該發生在隔離的副本裡，而不是直接改使用者的主要工作區。對本專案而言，執行狀態、公開 Wiki 與簡報產出、唯讀原始資料分別放在不同區域；三個區域的權限不同。

不可變計畫與分離層級

自我改進迴圈的文章提到「代理圖三大承諾」：不可變計畫（鎖定執行計畫，不隨模型即興改變）、分離層級（規劃、執行、恢復互為獨立角色）、嚴格升級（失敗恢復遵循預設協議且有重試上限）（用 DeepSeek V4 Flash 在 Codex 建立自我改進編碼循環 §代理圖三大承諾）。

這三點其實就是權限隔離的時間版本：

  • 不可變計畫：執行節點不能改大綱。
  • 分離層級：規劃者、執行者、恢復者不能是同一個角色。
  • 嚴格升級：失敗時只能照預設階梯升級，不能自己發明新流程。

反模式問題替代做法
所有節點共用一個大上下文事實容易混淆，錯誤難定位每個節點只給必要的輸入
渲染節點可以改文字忠實度審查被繞過渲染只能讀，不能寫事實

概念 · fallback-edges

退回邊與檢查前移：大圈少轉，小圈快轉

一句話：好的 Graph 不是沒有錯誤，而是錯誤在離源頭最近的地方被發現、被修掉。

兩種迴圈：小圈與大圈

課程把 Graph 裡的迴圈分成兩種（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.3）：

  • 小圈（Local Loop）：在單一節點內部或相鄰節點之間快速修正。例如逐頁稿節點內部跑「寫一頁 → 檢查出處 → 修改」，最多 2 輪；渲染節點跑「產生 HTML → 截圖 → 修版面」，最多 3 輪。
  • 大圈（Global Fallback）：從最後一關一路退回最前面的起點。例如簡報做到第 12 頁才發現「整個主題選錯」或「來源少了關鍵論文」，只好退回檢索重做。

黃金原則是：大圈很少轉，小圈轉得很快。大圈每次都很貴，應該極少發生；小圈在附近快速修，成本低、定位準（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.3）。

精準退回的四個例子

課程給了四個很具體的退回規則（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §5.3(3)）：

錯誤錯誤的修法正確的退回
第 6 頁結論講反整份簡報重生成只退回第 6 頁的逐頁稿，其他 12 頁不動
證據卡一開始就抽錯叫逐頁稿節點「自己想辦法」退回證據卡節點，重抽那一篇
第 5 頁字太多溢出把字縮到螞蟻大小硬塞退回逐頁稿，刪減文字
大綱缺一個重要子題等簡報做完才發現在大綱關卡退回檢索，補資料

這四個例子的共同點是：退回的目標是「錯誤的來源」，不是「最後的成品」。如果錯誤來自證據卡，修逐頁稿只是治標；如果錯誤來自大綱，修版面只是遮蓋。

檢查前移：為什麼要在大綱就抓錯

課程的核心診斷是：「錯誤必須在離源頭最近的地方被抓到。如果你的 Graph 常常在轉大圈，代表你的檢查關卡設得太後面了。」（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.3）

例如：

  • 如果等到 HTML 做完才發現「少讀了兩篇論文」，就要退回檢索、重抽卡、重寫大綱、重寫逐頁稿、重渲染——這是大圈。
  • 如果在大綱階段就檢查覆蓋率，發現少兩篇，只要退回檢索補卡，再修大綱——這是小圈。

這就是「檢查前移」：把檢查從成品端移到決策端。越早發現，退回成本越低。

退回邊怎麼設計

設計退回邊時，問三個問題：

  1. 這個錯誤的源頭是哪個節點？（檢索、證據卡、大綱、逐頁稿、渲染）
  2. 退回後要重跑哪些節點？（只重跑受影響的，不要整份重跑）
  3. 退回的上限是幾次？（超過就停止，請人類介入）

以本專案為例：

<G1 覆蓋率> ──不足──▶ 停止
<G2 大綱>   ──缺子題──▶ 退回 N1 補檢索
<G3 忠實度> ──某頁錯──▶ 退回該頁 N4
<G4 版面>   ──溢出──▶ 退回該頁 N4 刪字
<G5 獨立審查> ──覆蓋不足──▶ 退回 N2 補卡 → N4 補頁

每一條退回邊都指向「錯誤的源頭」，而且有次數上限。

退回的成本意識

退回不是免費的：每次退回都要重讀來源、重寫、重檢查，消耗 token 與時間。因此：

  • 小圈的上限要小（2–3 輪），避免在同一個問題上打轉。
  • 大圈的上限要更小（1 次），因為大圈通常代表規格或資料有問題，不是 AI 不夠努力。
  • 如果同一個錯誤改了 3 次還沒好，應該停下來檢查「規格是不是寫錯了」，而不是繼續重試（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.2）。

Harness 的 Detector 也提醒：偵測卡住要用「明確缺乏進展」當條件，並且先寫誤報測試；被忽略的警報等於沒有警報（How to Build An Agentic Harness using Kimi K3 §BUILD 09）。

反模式

反模式問題替代做法
所有錯誤都退回起點大圈一直轉，成本爆炸只退回錯誤源頭
用縮字/改 CSS 解決內容太多治標不治本，讀者還是看不懂退回逐頁稿刪減內容
沒有退回上限同一個錯誤無限重試設 2–3 輪上限，超過就停
檢查只放在最後錯誤太晚發現把檢查前移到證據卡、大綱、逐頁稿

教學用法

讓學生畫一條「簡報製作流程」，然後問：「如果第 6 頁的數字錯了，你要退回哪裡？」大部分學生會說「退回第 6 頁」；追問「如果這個數字是從證據卡就抄錯的呢？」學生就會發現需要區分「逐頁稿錯」與「證據卡錯」。這個練習可以很好地帶出「退回源頭」的概念。

概念 · verification

雙軌驗證：程式檢查與獨立 AI 審查

一句話：程式檢查負責「有沒有做到」，獨立 AI 審查負責「有沒有做對」；兩者都不能省。

為什麼「請 AI 檢查一下」不算驗證

課程有一句很重要的話：「說『檢查一下』不算驗證；說『做好一點』不算規格。」（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §6）因為「檢查一下」沒有定義檢查什麼、用什麼標準、誰來檢查、不通過怎麼辦。這種模糊指令會讓 AI 用「看起來差不多」的標準交差。

更嚴重的是，如果讓生成作品的同一個 AI 自己檢查，它會受到自己的生成脈絡影響，傾向於護航自己的產出。課程因此定下一條鐵則：獨立 AI 審查必須開啟全新對話，只給成品與原始來源（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.2）。

雙軌的分工

軌道檢查什麼誰來做通過標準
程式檢查頁數、出處、連結、數字、overflow、格式、測試Python / 測試腳本 / headless browser0 error；每個規則都有明確輸出
獨立 AI 審查忠實度、覆蓋率、教學結構、語氣、遺漏新上下文的 AI，只看成品與來源每個 fail 都有具體位置與理由

這兩軌不能互相替代：程式檢查抓不到「第 6 頁把論文 A 的結論講反」，獨立 AI 審查也無法穩定抓出「第 5 頁文字溢出 3px」。兩者互補，才是完整的驗證（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.2、§5.2）。

程式檢查：把主觀標準變成可執行規則

程式檢查的原則是：每一條規則都要能回答「哪裡錯、為什麼錯、怎麼修」。例如：

  • 簡報頁數是否在 8–15 頁之間？
  • 每一頁是否都有至少一個 wiki 引用與一個原始來源？
  • 引用的 wiki 頁面檔案是否真的存在？
  • 簡報上的百分比數字是否能在被引用的 wiki 頁找到？
  • 用 headless browser 渲染後，是否有元素超出投影片邊界？
  • 是否有外部 JS/CSS 依賴，導致離線或 GitHub Pages 失效？

本專案的 scripts/check_deck.py 與 scripts/render_check.py 就是這些規則的實作。檢查結果寫成 JSON，失敗時回傳非零退出碼，讓「通過」不是一句話，而是一個可重跑的結果。

獨立 AI 審查：新上下文、只看成品與來源

生成者會護航自己的產出；只有新上下文，才看得到自己的盲點。

獨立審查的流程：

  1. 開啟一個全新的對話（fresh context），不帶生成過程的記憶。
  2. 只給它「最終成品」與「被引用的 wiki 頁面」。
  3. 要求它逐頁檢查忠實度（有沒有講反、腦補、斷章取義）與覆蓋率（相關的重要來源有沒有漏掉）。
  4. 要求它輸出結構化的問題清單：頁碼、問題類型、原文依據、建議修法。
  5. 審查者不得動手改內容，只能產出報告。

這對應到 Anthropic 的 evaluator-optimizer 模式：生成者與評估者分離，評估者依明確標準給回饋（Building Effective AI Agents（Anthropic） §Workflow: Evaluator-optimizer）。

證據式前進：不要相信「我覺得完成了」

零信任的第一條規則是「僅基於證據前進」：程式碼、部署、測試通過才算進展；不要相信 agent 的文字描述，也不要把「執行完畢、退出碼 0」當成有做事（Agentic workflow 讓 GPT-3.5 在 HumanEval 達到 95.1% §零信任五規則）。

這條規則可以拆成三個實作：

  • 每個節點都有產出檔案：沒有檔案就沒有進展。
  • 每個檢查都有機器可讀的結果：不是「看起來可以」，而是 pass: true。
  • 每個失敗都有位置與理由：不是「再改好一點」，而是「第 6 頁的數字 37% 不在來源頁」。

驗證也要驗證自己：canary 與 fail closed

Harness 的工程文章提出一個很強的做法：沙箱要在啟動時用 canary 探針證明隔離，任一探針失敗就拒絕啟動，沒有降級模式（How to Build An Agentic Harness using Kimi K3 §BUILD 05）。同樣的道理可以用在簡報檢查：如果檢查腳本自己壞掉，不能默默跳過，而要 fail closed，讓我們知道「這次沒有驗證」。

另一個相關概念是「缺乏內建 eval 是 harness 的弱點」；課程提到 Hermes harness 需要自行整合 LangSmith/Langfuse 等觀測工具（前 Google 工程師的 AI Agent 系統設計課 §Agent Harness、記憶體系）。這提醒我們：驗證不是附加功能，而是系統的一部分。

反模式

反模式問題替代做法
生成者自己審自己自我護航、盲點新上下文獨立審查
只寫「請檢查」沒有標準，無法重跑寫成可執行規則與檢查清單
只看最終成品錯誤太晚才發現，退回成本高在證據卡、大綱、逐頁稿就設關卡
檢查腳本壞掉就跳過以為通過，其實沒驗證fail closed，腳本錯誤視為失敗
只檢查格式，不檢查語意版面漂亮但內容講反程式檢查 + 獨立 AI 審查

本專案的驗證設計

本專案有三道關卡：

  1. check_wiki.py：Wiki 結構、引用、孤兒頁、來源頁欄位。
  2. check_deck.py：頁數、每頁引用、百分比數字可回溯、無外部依賴。
  3. render_check.py：Edge headless 渲染、overflow、缺引用、截圖。

最後再加上一次獨立 AI 審查，並留下審查報告。只有三道程式檢查與獨立審查都通過，才進入交件。

  • [ ] 每一條完成標準都有對應的檢查方式？
  • [ ] 程式檢查是否會回傳非零退出碼？
  • [ ] 獨立審查是否使用新上下文，只給成品與來源？

  • [ ] 檢查腳本壞掉時是否 fail closed？
  • [ ] 是否在越早的關卡抓到錯誤越好？

比較 · prompt-loop-graph

Prompt、Loop、Graph 怎麼選？

一句話：不要問「哪個比較高級」，要問「這個任務需要多少結構」。

三種結構的比較

維度PromptLoopGraph
結構單一節點 A節點 A + 回到自己的邊 A ↺多節點 A → B → C + 條件邊 + 退回邊
誰決定下一步人類即時決定AI 在人類定的規格內決定人類事先畫好的流程決定
撰寫內容這一輪要做什麼目標、完成標準、驗證、停止規則節點、邊、條件、狀態、退回路線
撰寫次數每一輪都要寫寫一次，系統自動跑很多輪寫一次流程，可重複使用
出錯怎麼修人類肉眼發現、手動下指令整份再跑一輪修正錯在哪一關，退回哪一關
人在哪裡介入全程隨時在場最後驗收看報告事先指定的關鍵關卡（如大綱）
最適合一次性、個人臨時使用標準明確的重複性任務多階段、需精準退回的複雜任務
成本低（但人類時間高）中（token 較高）高（設計與維護成本高）

這張表改寫自課程的「結構選擇指南」（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.3），並補上成本與介入點的觀察。

決策樹

結構是為了重複與複雜度，不是為了好看。

這個任務會做幾次？
├─ 只做一次，而且我馬上會看結果
│   └─ 先用 Prompt
├─ 會重複做，而且每次的修正指令都差不多
│   └─ 升級成 Loop
└─ 會重複做，而且有多個階段、不同驗收標準、需要精準退回
    └─ 拆成 Graph

如果還不確定，先用 Prompt 做一次，觀察自己重複說了哪些修正指令；那些指令就是 Loop 的規格。如果 Loop 每次都要整份重跑，而且不同階段的檢查不一樣，那就是 Graph 的訊號（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.3）。

三種結構的實際例子

Prompt 的例子

「幫我把這段文字翻成英文。」這是一次性任務，人類馬上會看結果，不需要 Loop 或 Graph。

Loop 的例子

「每週把新文章整理成固定格式的筆記，直到通過格式檢查。」這是重複性任務，有明確的完成標準，適合 Loop。

Graph 的例子

「從 Wiki 檢索 → 抽證據卡 → 寫大綱 → 人類確認 → 寫逐頁稿 → 渲染 → 檢查 → 獨立審查。」這是多階段任務，每個階段有不同的驗收標準，且需要精準退回，適合 Graph（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §5.3）。

Loop 與 Graph 不是互斥

課程強調：「Graph 決定大流程，Loop 負責每一格內部的反覆修正。」（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §5.3(3)）一個 Graph 裡的每個節點，都可以自帶一個小 Loop。

例如：

  • 逐頁稿節點：寫 → 對來源 → 修改（最多 2 輪）。
  • 渲染節點：產生 HTML → 截圖 → 修版面（最多 3 輪）。
  • 獨立審查節點：審查 → 回報 → 退回（最多 1 輪）。

所以實務上常見的是「Graph 內含 Loop」，而不是二選一。

常見錯誤

錯誤為什麼會發生怎麼避免
用 Prompt 做重複性任務一開始沒想清楚任務會重複先做一次，觀察重複的修正指令
用 Loop 做多階段任務以為 Loop 可以處理所有事區分階段的驗收標準，拆成 Graph
用 Graph 做一次性任務為了炫技，過度設計先問「這個任務會做幾次？」
Graph 沒有退回邊只畫了往前，沒有畫往後每個檢查關卡都要有「不通過去哪」
Loop 沒有停止條件只寫了「做到好」補上硬上限、資料不足、成本

教學用法

給學生三個任務，請他們選 Prompt / Loop / Graph，並說明理由：

  1. 把一段文字翻成英文。
  2. 每週整理 5 篇論文成固定格式。
  3. 從知識庫生成一份 13 頁教學簡報。

通常第 1 題是 Prompt、第 2 題是 Loop、第 3 題是 Graph。追問「如果第 3 題只做一次，還需要 Graph 嗎？」可以帶出「結構是為了重複與複雜度，不是為了好看」。

檢查清單

  • [ ] 這個任務會做幾次？
  • [ ] 修正指令是否每次都差不多？
  • [ ] 是否有多個階段、不同驗收標準？
  • [ ] 是否需要精準退回？
  • [ ] 是否先用最簡單的結構，真的不夠才升級？

方法 · llm-wiki

LLM Wiki 的建置方法：給 AI 讀的知識庫

一句話：LLM Wiki 不是給人看的百科全書，而是給 AI 檢索的結構化記憶。

什麼是 LLM Wiki

課程引用 Andrej Karpathy 的 LLM Wiki 構想：它是一種 Context Engineering 的實踐，作用類似 RAG，但不需要先架設向量資料庫與 embedding 切塊程式（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §4.1）。

LLM Wiki 的重點不是「寫得很漂亮」，而是「讓 AI 能快速找到正確的頁面、正確的段落、正確的出處」。因此它的結構比文筆重要：

  • index.md 是檢索入口，列出所有頁面與主題。
  • sources/ 一篇來源一頁，保留原始 URL 與可引用主張。
  • concepts/ 跨來源綜整概念，每個事實都連回來源。
  • comparisons/ 並陳不同做法，幫助選擇。
  • methods/ 記錄可重複的流程。
  • glossary.md 統一術語。
  • log.md 記錄何時 ingest 了什麼、改了哪些頁。

為什麼要「先討論、後生成」

課程比較了兩種建 Wiki 的方式（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §4.1）：

  • 一句話生成：把 Karpathy 的 gist 丟給 AI，說「幫我建 Wiki」。一秒建好，但長出來的是通用規則，不符合你的主題。
  • 先討論、後生成：先讓 AI 訪談你 8–10 題，釐清讀者、頁面類型、語言、出處粒度、衝突處理、ingest 模式、下游應用、lint 規則；整理成需求摘要，確認後才建立專案規則與資料夾。

差別在於：前者是「通用模板」，後者是「你的工作流」。LLM Wiki 的價值在於貼合你的領域，而不是套用別人的結構。

Ingest 的標準流程

  1. 把原始資料放進獨立資料夾，設為唯讀。
  2. 一次讀一篇，寫 wiki/sources/<id>.md：
  • frontmatter：original_url、raw_file、ingested、reliability。
  • 摘要：這篇在說什麼、為什麼重要。
  • 可引用主張表：主張、原文位置、本 Wiki 用到的地方。
  • 限制與注意：這篇的偏誤、二手性質、過期風險。
  1. 更新相關的 concepts/、comparisons/、methods/ 頁，補上 sources/&lt;id&gt; 引用。
  2. 更新 index.md 的頁面清單與 log.md 的 ingest 紀錄。
  3. 執行 python scripts/check_wiki.py，修到 0 error。

引用粒度

本專案的引用規則是：

  • 每個事實句至少一個 sources/&lt;id&gt;。
  • 數字、百分比、年份、頁數、輪數，必須能在來源頁找到。
  • 引用原文時用 > 區塊，保留原文，不改寫。
  • 來源頁的「可引用主張」表要標原文位置（章節或段落）。
  • 簡報每頁 footer 至少一個 wiki 連結與一個原始 URL。

這樣做的目的是：當讀者質疑「這句話哪來的」時，可以從簡報 → wiki → 來源頁 → 原始 URL，一路追下去。

衝突處理

LLM Wiki 一定會遇到來源衝突。本專案的原則是「並陳，不選邊」：

  1. 同一段列出雙方說法。
  2. 標註年份、實驗條件、樣本差異。
  3. 如果無法判斷，明確寫「兩篇說法不同，尚無共識」。
  4. 不把其中一方寫成「錯的」，除非有更強的來源。

這樣做的好處是：讀者可以看到爭議，而不是被單一說法誤導。

Lint：Wiki 的健康檢查

scripts/check_wiki.py 檢查以下項目：

  • frontmatter 必填欄位（id、title、type、updated、sources）。
  • id 唯一。
  • index.md 收錄所有頁面。
  • 所有 ... 連結可解析。
  • 沒有孤兒頁（沒有被 index 或其他頁連結）。
  • 來源頁有 original_url、raw_file、至少 3 條可引用主張。
  • 概念頁至少引用 2 個來源。
  • 沒有未完成的佔位文字。
  • 沒有常見簡體字。

這些檢查讓 Wiki 不會隨著時間腐化：新增頁面時，index 與連結會自動被要求更新；引用斷掉時，lint 會報錯。

一句話：這份簡報不是「一句話生成」，而是 7 個節點、5 個關卡、3 輪檢查的產物。

為什麼不用一句話 Prompt

一句話 Prompt 也能生出 HTML，但常見的結果是：排版爆版、數字沒出處、只讀了部分來源、把結論講反（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §5.1）。這些問題不是模型不夠強，而是沒有把「檢索、整理、檢查、退回」寫進流程。

因此本專案採用 Graph 版：先把 Wiki 建好，再用 7 個節點生成簡報；每個節點都有明確的輸入、輸出與檢查。

為什麼這樣設計

1. 大圈很少轉，小圈快轉

只有 G5 失敗且問題在源頭時，才退回 N1/N2；大部分錯誤在 N4 或 N5 的小圈內修掉。逐頁稿與渲染各自有 2–3 輪上限，錯誤在離源頭最近的地方被抓到（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.3）。

2. 權限隔離

證據卡不能看別篇、逐頁稿不能看卡片外、渲染不能改字、審查不能動手。這樣可以避免後面階段偷改前面的事實（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §5.3(2)）。

3. 雙軌驗證

程式檢查負責客觀條件（頁數、出處、數字、overflow），獨立 AI 審查負責語意品質（忠實度、覆蓋率）。生成者不審自己（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.2）。

4. 停止條件

修改滿 3 輪、相關來源 < 3、數字找不到來源、overflow 修不好、檢查腳本 crash，都會停止並附報告（Week 10 課程筆記：把你的工作拆成 AI 能做的流程 §3.2）。

這篇筆記整理兩件事：第一，如何在 Codex 裡用三個模型建立自我改進的編碼循環——DEEPSEEK 執行任務、LUNA 評估並寫入 log.md、SOL 依評估重寫 prompt.md；並用 watcher.md 與 rewriter.md 限制程式碼不超過 12 行、prompt 增長不超過 20%。第二，一套 10 週的 Graph Architect 課程，涵蓋知識圖譜、實體解析、代理圖設計與作品集。

對本 Wiki 最重要的是「迴圈要有紀錄與預算」：log.md 是評估紀錄，prompt.md 是下一輪的輸入，watcher.md / rewriter.md 是防止迴圈失控的規則。這正是 Loop Engineering 的具體樣貌：不是無盡重試，而是每一輪都留下可檢查的狀態。
